## Deliverables
`src/core/index.ts` exporting `createCoreServices(db: GameDatabase): CoreServices` (exactly the contract interface), built from:
1. **rng.ts** — mulberry32 step: `next(rng) → { value: 0..1, rng }`.
2. **progression.ts** — stats at level (base + growth × (level−1), floored), xp curve, level-ups, skills by level.
3. **gear.ts — Dual-Archetype Gear Engine.** `standard` returns flat stats. `relic`: `stats + perLevel × curve(level−1) + perLiberatedRegion × regions`, floored, clamped by `cap`; curves: linear `n`, sqrt `√n × 3`, log `ln(1+n) × 4` — document them. `signature`: flat stats + contributes a hook. Hook registry keyed by `CombatHookId`; must implement `HOOK_COUNTER_ATTACK` (params `chance`, `power`): when the owner survives a single-target *physical* hit from an enemy, roll rng < chance → immediate basic-attack counter at `power`×, emitting a `hook` event then normal attack/damage events. Counters never trigger other counters. Design the registry so new hooks are one file each.
4. **fusion.ts — Decorator pattern.** A `ProfileComponent` interface, a `BaseHeroProfile` concrete component, and a `SpiritDecorator` wrapping any component (one generic data-driven decorator class is fine, plus a resonance decorator applied when both partners are in the stack). `compose` folds the spirit list innermost-first: multipliers then flat bonuses per layer, affinities multiplied, skills unioned (stable order, deduped), outermost layer sets `basicAttackElement`, `armorMax` = sum of layer armor, `layers` has one readable line per layer. Stack limit `FUSION_MAX_STACK`, no duplicate spirits, spirit must be in hero `fusionAffinity`, owned and `awakened`. Order must matter observably (e.g. [ashka, mirelle] ≠ [mirelle, ashka]).
5. **combat/** — the turn-based state machine. Phases per contract. Round order by effective spd desc (id tiebreak), recomputed each round. `step` validates the action for `activeId`; invalid → append `invalid` event only. Damage: physical `atk×power×(100/(100+def))`, magical with mag/res, × affinity, × guard (0.5), crit from luck, min 1, ±variance from rng. Statuses tick at the owner's turn start (burn DoT, regen, stun skips, durations decrement). Dead combatants are skipped; victory/defeat detection after every resolution; victory computes `rewards` (xp, coin, rng-rolled drops, `liberatesRegion`). Flee uses rng vs relative speed, disallowed when `canFlee` is false. After a party action resolves, the machine advances to the next combatant; phase is `enemyTurn` when an enemy is active (the app then calls `chooseEnemyAction` + `step`) and `awaitingInput` for heroes.
   - **Armor Break:** damage to a fused, unbroken host first chips `fusion.armor` by the *full pre-armor damage* while the host still takes 70 % of it (`absorbedByArmor` = the 30 %). At armor 0 → `armorBreak` event, `broken = true`, `brokenTurns = FUSION_BREAK_TURNS`; the host uses un-fused stats/skills/affinities. Decrement at each of the host's turn starts; at 0 → `armorRestore`, armor refilled. Fusion is never permanently lost.
   - **Dragon Transformations (Sync/AP):** sync gains: +12 on acting, +8 on being hit, + skill `syncGain`, capped 100. `transform` needs the form unlocked by level, `sync ≥ syncRequired`, `ap ≥ apCostToEnter`; it consumes the turn. While in form: form `statMultipliers`/`affinities`/`skills` apply, and at each of the actor's subsequent turn starts `apDrainPerTurn` is paid — if unaffordable, or `turnsInForm ≥ maxTurns`, auto-`revert` (event with reason) and the actor still acts that turn in base form. KO reverts. Revert sets sync to 0. Transformation suppresses fusion bonuses while active (document this) but keeps the armor pool.
   - **AI:** `chooseEnemyAction` is deterministic from state: prefers a usable skill when `hash(rng, round) < skillBias`, targets lowest-HP-fraction alive hero.
6. **quests.ts — World Flag / Quest State Machine.** Fold events into flags using the canonical keys documented on `WorldEvent` (counts). `dispatch` then loops to a fixpoint: HIDDEN→DISCOVERED (`discoverWhen`), DISCOVERED→ACTIVE (`activateWhen`), objective completion (sticky once true), ACTIVE→COMPLETED (all non-optional objectives) — emitting notifications and collecting rewards; `flag` rewards are applied to flags immediately and can cascade. Transitions are strictly forward and at most one status step per quest per pass (a quest can chain multiple steps in one dispatch across passes). Completing a quest sets `quest:<id>` = `'COMPLETED'` style flags for every status change (`quest:<id>` = status string).
